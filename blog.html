FIELD NOTE_001ACTIVE DIRECTORY6 MIN READ

Active Directory Enumeration: Start With the Map

When assessing an Active Directory lab, it is tempting to jump straight into attack tooling. A better first step is to understand the environment: its domain structure, identities, group relationships, hosts, and the trust boundaries connecting them. Good enumeration turns a pile of output into a set of testable hypotheses.

1. Confirm the scope and your starting point

Record the authorized domain, in-scope hosts, your current account privileges, and any rules of engagement. In a lab, note which machine and network segment you are operating from. Do not scan systems outside the agreed scope.

2. Build an identity and host inventory

Use approved, low-impact queries to identify domain controllers, DNS configuration, domain users and groups, computer accounts, and relevant service accounts. Keep the raw output and timestamp it so findings can be reproduced.

# Example: inspect domain context from a Windows lab host whoami whoami /all echo %USERDOMAIN% nltest /dsgetdc:%USERDOMAIN%

These commands are starting points for a Windows domain lab. Availability and results depend on the host configuration and current permissions.

3. Follow relationships, not just object names

Prioritize relationships that may affect security: nested group membership, delegated permissions, service accounts with excessive rights, privileged sessions on workstations, and permissions over Group Policy Objects. Graph tools such as BloodHound can help visualize relationships, but a graph edge is a lead to validate—not proof that a path is exploitable.

4. Turn observations into findings

  • Observation: describe the exact object, permission, or relationship.
  • Validation: explain how it was confirmed within scope.
  • Impact: state what an attacker could do if the condition is abused.
  • Remediation: remove unnecessary rights, tighten delegation, rotate exposed credentials, or reduce privileged account exposure as appropriate.
Field rule: enumerate methodically, validate every assumption, and document the evidence needed for another tester to reproduce the finding.

FIELD NOTE_002THREAT INTELLIGENCE5 MIN READ

Phishing Triage: More Than a Suspicious Link

A suspicious email is a collection of signals, not a verdict based on one URL. A disciplined triage workflow preserves evidence, looks for corroborating indicators, and avoids accidentally interacting with attacker-controlled infrastructure.

1. Preserve the message

Keep the original message or approved export, including full headers and timestamps. Record who received it and whether anyone clicked a link, opened an attachment, replied, or entered credentials. Follow your organization's evidence-handling policy.

2. Review sender authentication and routing

Inspect the visible From address alongside Return-Path, Reply-To, and the Received chain. Review SPF, DKIM, and DMARC results, while remembering that authentication passing does not automatically make a message trustworthy. Look for lookalike domains, unexpected reply destinations, and inconsistencies with the claimed sender.

3. Analyze URLs and attachments safely

  • Extract and normalize URLs without opening them in a normal browser session.
  • Check domain age, reputation, redirects, and related indicators using approved threat-intelligence services.
  • For attachments, record file type, hashes, and metadata in a controlled analysis environment.
  • Do not upload confidential messages or customer files to public scanners unless policy permits it.
Triage record - Sender / Reply-To: - SPF, DKIM, DMARC: - URLs and domains: - Attachment names and SHA-256: - Reputation sources checked: - User interaction reported: - Confidence and next action:

4. Decide and communicate

Correlate the evidence before classifying the message. If malicious, follow incident-response procedures to contain affected accounts, remove matching messages where appropriate, block validated indicators, and reset credentials or revoke sessions when exposure is suspected. Share a short explanation with users so they know what to report next time.

A reputation score is one input—not a substitute for context, evidence, and analyst judgment.

Cloud Metadata Services: Reduce the Exposure

Cloud instance metadata services can expose useful information to workloads, including temporary credentials in some configurations. If an application can be tricked into making requests to internal addresses, a server-side request forgery (SSRF) flaw may become a path toward metadata access. The exact risk depends on the cloud provider, metadata configuration, workload identity, and permissions attached to the instance.

Why it matters

Metadata endpoints are often reachable from within a virtual machine or workload network. An SSRF vulnerability that allows arbitrary or insufficiently restricted outbound requests can potentially reach destinations the application developer did not intend. If credentials are exposed, excessive IAM permissions can amplify the impact.

Defensive checklist

  • Require hardened metadata access: use the provider's recommended protections, such as IMDSv2 on AWS where applicable, and enforce them through policy.
  • Constrain outbound requests: use allowlists, destination validation, redirect controls, and network-level egress restrictions where practical.
  • Use least privilege: grant workload identities only the permissions required for their task; avoid broad wildcard permissions.
  • Keep secrets out of responses and logs: never return raw metadata or credentials to users, and avoid logging sensitive tokens.
  • Monitor and rotate: alert on unusual credential use, investigate suspicious access, and revoke or rotate credentials when exposure is suspected.
  • Test safely: validate SSRF defenses in a controlled environment with non-sensitive test targets and explicit authorization.

Review questions for a cloud assessment

  1. Can user-controlled input influence the destination of server-side requests?
  2. Are redirects and alternate IP representations handled safely?
  3. Can the workload reach metadata endpoints, and what protections are enforced?
  4. What permissions would temporary workload credentials provide?
  5. Are unusual API calls logged, alerted on, and tied to a workload identity?
Defense in depth matters: block unintended requests, harden metadata access, minimize identity permissions, and monitor credential use together.
